# Source-Watcher Stress Report — 60% DOM Rewrite

> **Status:** Live evidence + remediation plan.
> **Audience:** Anyone deciding what to do when a real upstream
> ships a redesign that touches variable names, headers, container
> tags, and the basic DOM elements every scraper has hard-coded.
> **Reproducible:** every transcript below is generated by
> [`_demos/source_watcher_60pct.py`](_demos/source_watcher_60pct.py)
> — run it yourself with `python3 docs/testing/_demos/source_watcher_60pct.py`.
> **Doctrine:** AGENTS.md §2 rules 7 (adversarial tests are first-class)
> and 8 (phase gates).

This document answers, with running code, a concrete question:

> *"What does the Source-Watcher actually do when ~60% of a site's
> DOM structure changes — class names rewritten, `<header>` swapped
> for `<div class="topbar">`, `<article>` swapped for `<li>`,
> `data-match-id` renamed to `data-fixture-id`, an `<h2>` dropped, a
> sponsor block added, etc.?"*

The short answer up front: **today's watcher under-classifies that
change as `semantic`** because the production capture mode only sees
a four-field envelope (`_status`, `_raw_len`, `_sha256`, `_suffix`)
and the byte size barely moved. The fix is identified, sized, and
on the roadmap (see §5).

---

## 1. Scenario

We compare two snapshots of the same mackolik fixtures page.

**v1 — current production markup (excerpt):**

```html
<header class="site-hdr">
  <nav class="primary-nav">…</nav>
</header>
<main class="content">
  <h1 class="page-title">Süper Lig — Hafta 30</h1>
  <h2 class="section-title">Maç Programı</h2>
  <section class="match-list" data-week="30">
    <article class="match" data-match-id="20260420-001">
      <span class="kickoff">20:00</span>
      <span class="home-team">Galatasaray</span>
      <span class="away-team">Fenerbahçe</span>
    </article>
    …
  </section>
  <h2 class="section-title">Puan Durumu</h2>
  <table class="standings">…</table>
</main>
```

**v2 — after a redesign that touches ~60% of the selectors a scraper
would use:**

```html
<div class="topbar">
  <ul class="menu">…</ul>
  <aside class="sponsor-strip">…</aside>          <!-- new block -->
</div>
<section class="page-body">
  <h1 class="hero__heading">Süper Lig — Hafta 30</h1>
  <h3 class="block__title">Maç Programı</h3>      <!-- h2→h3 demoted -->
  <div class="fixtures-grid" data-gw="30">        <!-- attr renamed -->
    <ul>
      <li class="card" data-fixture-id="20260420-001">  <!-- attr renamed -->
        <time class="card__time">20:00</time>
        <p class="card__home">Galatasaray</p>
        <p class="card__away">Fenerbahçe</p>
      </li>
      …
    </ul>
  </div>
  <ol class="leaderboard">                        <!-- table → ol -->
    <caption class="leaderboard__cap">Puan Durumu</caption>
    …
  </ol>
</section>
```

**What changed, classified by what a scraper cares about:**

| Concern | v1 | v2 | Risk to scraper |
|---|---|---|---|
| Page section wrapper | `<main class="content">` | `<section class="page-body">` | Selector miss |
| Hero heading class | `page-title` | `hero__heading` | Selector miss |
| Section heading | `<h2 class="section-title">` | `<h3 class="block__title">` | Heading-tag + class miss |
| Fixture container | `<section class="match-list">` | `<div class="fixtures-grid">` | Selector miss |
| Per-fixture wrapper | `<article class="match">` | `<li class="card">` | Selector miss + tag change |
| Team name spans | `home-team` / `away-team` | `card__home` / `card__away` | Selector miss |
| Kick-off element | `<span class="kickoff">` | `<time class="card__time">` | Selector + tag miss |
| Match ID attribute | `data-match-id` | `data-fixture-id` | **Identity-key miss** ⚠ |
| Standings | `<table class="standings">` | `<ol class="leaderboard">` | Whole-table parse breaks |
| New sponsor block | — | `<aside class="sponsor-strip">` | Noise, unlikely to confuse |
| CMS generator meta | `mackolik-cms@4.2` | `mackolik-cms@5.0` | Confirms major-version bump |

By any reasonable measure this *is* a schema-breaking redesign for the
scraper. The question is whether the watcher classifies it that way.

## 2. Live transcript — what the watcher actually emits

Run produced **2026-04-20**, against
[`ai/swarm/source_watcher/`](../../ai/swarm/source_watcher/) at
`source_watcher` v1.4.0. Three paths fed through the same
`differ → classifier → planner` pipeline:

### Path A — production envelope (what `watch.run` records today)

```
v1 raw_len = 1776, v2 raw_len = 1834, delta = 58 bytes (+3.3%)

raw FieldDiff count: 3
plan.severity:       semantic
plan.actions:        ['run_parity_tests', 'refresh_fixtures']
plan.summary:        mackolik: 3 semantic change(s); rerun parity + refresh fixtures
classified diffs:
  [semantic]  changed  $._raw_len   — value changed at $._raw_len
  [semantic]  changed  $._sha256    — sha256 followed raw_len severity (semantic) at $._sha256
  [semantic]  changed  $._suffix    — value changed at $._suffix
```

> ⚠ **The 60% DOM rewrite is classified `semantic`, not
> `schema_breaking`.** Action plan: rerun parity + refresh fixtures.
> No human is paged. This is the gap §5 fixes.

**Why:** the envelope only carries four fields. `_raw_len` only
shifted 3.3% (well above the 1% cosmetic floor, well below the 80%
collapse ceiling), so the cross-diff rule degrades the `_sha256`
signal to "follows raw_len severity" → semantic.

### Path B — same redesign, served behind a Cloudflare-style soft block

```
raw FieldDiff count: 3
plan.severity:       schema_breaking
plan.actions:        ['run_parity_tests', 'open_ticket', 'page_human']
plan.summary:        mackolik: 3 schema-breaking change(s); HUMAN ATTENTION REQUIRED
classified diffs:
  [schema_breaking]  changed  $._raw_len  — raw_len collapsed (old=1776, new=142) at $._raw_len
  [schema_breaking]  changed  $._sha256   — sha256 followed raw_len severity (schema_breaking) at $._sha256
  [semantic       ]  changed  $._suffix   — value changed at $._suffix
```

> ✅ The watcher correctly escalates to `schema_breaking` here. The
> 80%-raw_len-collapse rule (added in the 2026-04-20 stress refactor)
> catches the challenge-page substitution cleanly.

### Path C — hypothetical parsed-DOM view (not in production)

If `watch.run` were taught to capture a coarse structural fingerprint
(`{tag_counts, class_set, data_attrs}`) instead of (or alongside) the
byte envelope, the same v1 → v2 redesign produces:

```
raw FieldDiff count: 40
plan.severity:       schema_breaking
plan.actions:        ['run_parity_tests', 'open_ticket', 'page_human']
plan.summary:        mackolik: 40 schema-breaking change(s); HUMAN ATTENTION REQUIRED
```

> ✅ Forty distinct FieldDiffs in the class-set + data-attr lists →
> the existing **bulk-list-truncation cross-diff rule** (>5 sibling
> removals from one parent list) escalates to `schema_breaking`.
> **The classifier already has the right rules — it just needs richer
> input.** This is the smallest viable improvement (§5.1).

## 4. Shortcomings — what the demo exposes

Each is reproducible with the demo script above; remediation is
sized in §5.

| # | Shortcoming | Symptom in Path A | Why it matters |
|---|---|---|---|
| **S1** | **Envelope is too coarse for HTML.** Four scalar fields (`_status`, `_raw_len`, `_sha256`, `_suffix`) cannot represent "the DOM was 60% rewritten while the byte count happened to land in the same neighbourhood." | 60% rewrite → severity `semantic`, not `schema_breaking` | The whole purpose of the watcher is to catch exactly this case before the scrapers silently start parsing nothing. |
| **S2** | **No tag/class/attribute fingerprint in production captures.** The watcher knows nothing about "set of CSS classes present" or "set of `data-*` attributes used." | All three Path A diffs collapse to the four envelope keys | A scraper-relevant signal is sitting one parser-call away from being usable. |
| **S3** | **`_suffix` (last 120 chars) is a weak last line of defence.** It catches footer + closing-tag changes but the *interesting* DOM lives in the middle of the page. | `_suffix` did diff, but only as `semantic` | Easy to add a `_prefix` + `_anchor_set` companion. |
| **S4** | **No baseline learning.** Day-to-day raw_len wiggle is currently benchmarked against a single fixed threshold (1% floor / 80% ceiling). | A site with chronic 5–10% byte-size jitter will never trigger the cosmetic rule even when nothing real changed | Per-source learned percentile band would silence the noise. |
| **S5** | **No per-source severity overrides.** A fixture page redesign is a P1; a footer-link reshuffle is a P3. Today's classifier treats all sources identically. | Same `semantic` verdict regardless of which source moved | Adds operator burden; not architecturally hard. |
| **S6** | **Plan is fire-and-forget.** `actions = [run_parity_tests, refresh_fixtures]` is published, but nothing in the agent confirms those actions actually happened. | Reactor wiring is Phase 4.7 work, not done yet | Without wiring, breaking changes surface only via downstream failures. |
| **S7** | **No correlation with the (separate) Content-Freshness signal.** A real redesign usually shows up as both *structural drift* (watcher) *and* a sudden flood of `record.retracted` / extractor degraded events. | Today the two agents are independent | CONTENT_FRESHNESS §15.6 plans the bidirectional link; not yet implemented. |
| **S8** | **Tested at fixture scale only.** All current tests run on hand-crafted seed envelopes. We have no test that fetches a real `*.local` mock vhost end-to-end through the scheduler. | Demo script bypasses the scheduler | Mock-vhost integration test would close the loop. |

## 5. Improvements — sized and sequenced

These are in order of **value-delivered ÷ change-required**. Items
1–3 are mechanical; 4–6 are roadmap-scope.

### 5.1 Add a `_dom_fingerprint` to the HTML envelope *(smallest viable fix, blocks the demo's S1 + S2)*

Augment `watch.run` so HTML probes record one extra field:

```python
{
    "_status":          200,
    "_raw_len":         1776,
    "_sha256":          "…",
    "_suffix":          "…",
    "_dom_fingerprint": {
        "tag_counts": {"div": 3, "section": 1, "article": 3, "h2": 2, …},
        "class_set":  ["site-hdr", "primary-nav", "match-list", …],
        "data_attrs": ["match-id", "week"],
    },
}
```

The classifier already has the cross-diff rule that escalates ≥6 sibling
list removals to `schema_breaking` (Path C in the demo proves it).
**No classifier change required.** Cost: one `selectolax` parse per
HTML probe (~5 ms on the demo page) and a small bump to snapshot
size (~1 KB).

**Doctrine fit:** stays inside AGENTS.md §2.8 (deterministic core);
no LLM in the path; pure function over input bytes.

### 5.2 Add `_prefix` and `_anchor_set` companion fields *(rounds out S3)*

`_prefix` mirrors `_suffix` for the head of the document; `_anchor_set`
captures `{a[href], img[src], link[rel=canonical]}` URLs. These are the
fields most often touched by CMS migrations even when the body looks
visually identical.

### 5.3 Per-source learned-baseline mode *(removes S4)*

For each source, record the rolling P50 / P95 / P99 of `raw_len` deltas
across the last `N` snapshots (default `N=200`). Promote a `raw_len`
delta to `schema_breaking` when it lands above the source's own P99 by
more than a configurable factor (default 3×). Falls back to today's
fixed thresholds when fewer than `N` snapshots exist.

Storage: 8 floats per source in the snapshot index. Memory: trivial.

### 5.4 Wire the reactors *(closes S6)*

This is exactly the Phase 4.7 work just added to ROADMAP. The watcher
publishes `source.schema_breaking` events; a `parity-reactor` runs the
parity test suite; a `ticket-reactor` opens a tracker row; a
`page-reactor` notifies the on-call. Idempotent on `event_id` per
CONTENT_FRESHNESS §15.2.

### 5.5 Bidirectional Source-Watcher ↔ Content-Freshness link *(closes S7)*

Per CONTENT_FRESHNESS §15.6: the freshness agent subscribes to
`source_watcher.schema_breaking` and pauses captures for the affected
source until human ack; the watcher subscribes to freshness's
`source.degraded` to escalate severity (drift + degradation = P1).

### 5.6 Mock-vhost end-to-end integration test *(closes S8)*

Add `tests/test_e2e_mock_vhost.py` that:
1. Snapshots `https://mackolik.local/` via the production scheduler.
2. Mutates one of the seed files in `infra/mock/seeds/mackolik/`.
3. Re-runs the scheduler.
4. Asserts the resulting plan has the expected severity.

This is the smallest test that exercises *everything* — capture, store,
diff, classify, plan — against the real Phase 2 infra rather than
hand-crafted dicts.

## 6. Decision recommendation

The demo concentrates the entire question on one number: **3.3%**.
That's how much `raw_len` moved on a 60% structural rewrite. Today's
classifier — correctly, given its inputs — calls that `semantic`.

**Recommended path:** ship §5.1 first (one extra envelope field, no
classifier change, mechanical PR). It promotes the Path A verdict
from `semantic` to `schema_breaking` and pages a human exactly when
one is needed. Items §5.2–§5.6 follow at their natural roadmap
positions.

**Tracker note when shipped:**

```
make track.add PHASE=2 STATUS=in-progress \
  NOTE="source_watcher: add _dom_fingerprint envelope field (closes S1/S2 from 60pct stress demo)"
```
